# Evaluations

Each folder holds a claim set. Each `run_*.py` re-runs one set and writes `results/*.json`. Results here are one person's laptop on one day.

## Planted errors: what the number means

`planted/` has 40 claims, 20 true and 20 with one planted error, generated by `planted/make_claims.py` and frozen before the run. The same proof template is used for a true claim and its planted partner.

```bash
python evals/run_planted.py     # one claim at a time, 20 to 70 minutes on a laptop
```

Result, 2026-11-02, one run on a Windows laptop, Lean 4.34.1, commit `9d42599`, 2,504 s wall: **0 of 20 planted claims passed and 0 of 20 true claims failed.** The planted claims stopped at stage `elaboration` (18) or `dimension` (2). Raw rows: `results/planted.json`.

**The caveat that belongs beside that number.** Every planted error is in a goal value, so a planted claim is a false theorem, and Lean refusing it follows from Lean's soundness once the statement is generated. The families named "dropped term" and "radial-only" test the goal number, not the modelling error itself. This result shows the plumbing works. It does not show the tool catches modelling errors, and errors in a statement's premises are not in this set. The planted errors were designed by the tool's author, and an outside audit is owed.

The planted claims stop at stage `elaboration` or `dimension`, not stage `kernel`: no tactic could finish a false goal, so no term reached the kernel. What the kernel adds is on the passes, where it accepted the term.

## Baseline: the same claims without Lean

`run_baseline.py` gives the 40 claims to one model in one prompt, shuffled, with the intent text removed because it names the planted error. The model is run three times per prompt.

```bash
python evals/run_baseline.py --agent "claude -p --model sonnet --setting-sources project --strict-mcp-config --permission-mode dontAsk" --runs 3  # as recorded; use --safe-mode, see docs/claim-format.md
python evals/run_baseline.py --no-definitions --agent "..." --runs 3
```

Result, 2026-11-02, Sonnet through the `claude` CLI, three runs per prompt:

| Prompt | Planted claims called true | True claims called false |
|---|---|---|
| With the definitions each claim uses | 0 of 20, every run | 0 of 20, every run |
| Without them (`--no-definitions`) | 4 of 20, every run: all four `geom_planted` | 0 of 20, every run |

Raw replies: `results/baseline.json` and `results/baseline-no-definitions.json`.

Read that plainly: on simple planted arithmetic a careful model with a well-written prompt ties Lean. This set does not show Lean beats a model at finding errors. The difference it does show is that the model's score moved with the wording of the prompt, and that its answer is a sentence you have to trust, while a kernel run is a result you can re-run, with the assumptions listed. Temperature and model version were whatever the CLI used that day.

## Translation gap: does the formal statement say what the English says?

Every claim in `translation/` is true mathematics, so Lean should pass all 12. Six were written to disagree with their English intent: a GB where the intent says GiB, a range cut short, a reversed inequality, contradictory premises, an assumption that is the conclusion, and a looser number. The other six are faithful. The audit is blind: one agent run reads only the Lean and writes English, a second reads only that English and the intent. The theorem is renamed `claim` in what the first run sees, because names such as `capacity_flipped` would give the answer away.

```bash
python evals/run_translation.py --agent "claude -p --safe-mode --model sonnet --strict-mcp-config --permission-mode dontAsk"
```

Result, 2026-11-02, one run, Sonnet through the `claude` CLI for both audit steps:

| | Mistranslated (6) | Faithful (6) |
|---|---|---|
| Lean kernel passed the statement | 6 | 6 |
| Blind audit said "does not match" | 6 | 1 (a false alarm: `disk_units_ok`) |

Lean passed every mistranslated claim, as it must: each one is true mathematics. The audit caught all six and raised one false alarm: in `disk_units_ok` the judge read the bit-converted constants as a different claim. An earlier run of the same set, before the theorem name was hidden from the reader, also caught six and raised two false alarms, so treat the false-alarm rate as noisy. Raw replies: `translation/audit/` and `results/translation.json`.

Twelve claims and one run is a small sample, written by the tool's author. It shows the size of the gap and that the audit is doing something. It is not an error rate. The mistranslations are also deliberate, and a real one may be subtler. Translation from English by a model, where the model writes the YAML itself, is not measured here: these YAML files were written by hand.

## Agent proofs

`agent/` has three claims with no proof on disk: two true, one false.

```bash
python evals/run_agent_proofs.py --agent "claude -p --safe-mode --model sonnet --strict-mcp-config --permission-mode dontAsk"
```

Result, 2026-11-02, one run, Sonnet, up to two attempts per claim: both true claims got a proof the kernel accepted on the first attempt. On the false one the agent answered `UNPROVABLE` with a counterexample (f = 1/20, n = 100), so nothing reached Lean. Raw rows: `results/agent-proofs.json`.

Three claims and one run says the loop works end to end. It says nothing about how often an agent can prove harder claims.

## Not measured

- A wrong translation in the wild, where a model writes the claim from a real document.
- A wrong assumption: a NUMBER or FIT that is false in the world. The verdict lists it and stops there.
- Any comparison with another verification tool. None was run.
